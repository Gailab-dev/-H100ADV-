# H100 개발서버 이전 런북 (Docker 일괄)

> [!note] 범위 (2026-10-23 결정)
> - 오늘은 **런북·스크립트 준비까지**. 서버 변경은 하지 않았다.
> - 이전 방식: **Docker 컨테이너로 한 번에**(module_c + Java/Tomcat9 + DB). 10-13 권고(2단계)와 다른 선택이므로 §1 게이트를 반드시 통과해야 한다.
> - 실행 주체: 스크립트는 작성, **실행은 효성님**. 구 서버(192.168.0.15)는 읽기 전용, 정지·재기동은 사람이 직접.
> - 디바이스 전환 방식(IP 인수 vs .115로 설정 변경): **미정** → §5에 A/B 두 경로 모두 수록.
> - 비밀값은 이 문서·스크립트에 없다. `/etc/h100/*.env`(640 root:h100)에서만 주입.

## 0. 목표 구성

| 구성 | 컨테이너 | 게시 포트 | 비고 |
|---|---|---|---|
| module_c (Go) | `h100-module-c` | 0.0.0.0:8189 | 디바이스 TLS 직접 수신. 접근제어는 **DOCKER-USER**(45) |
| Java 웹 (Tomcat 9/JDK 17) | `h100-web` | 127.0.0.1:8300→8080 | 기존 nginx `upstream was_9`(127.0.0.1:8300) **변경 없음** |
| DB (MariaDB 10.11) | `h100-db` | 127.0.0.1:3310→3306 | 컨테이너 간은 `db:3306`. 앱 계정 `h100_module_c`, `h100_web` (172.31.100.% 한정) |
| 미디어 | 볼륨 `/var/lib/h100/media` | – | 하위폴더 5개, UID:GID 3100:3100, 디렉터리 2775 / 파일 664 |

- 기존 `mariadb-legacy`(3308), 호스트 MariaDB(3306), 시험 설치 `h100_module_c`(systemd, 8189), `was-9`는 **그대로 두되**, 8189·8300 충돌만 정리한다.
- 디바이스→서버 8189는 DNAT를 거치므로 **INPUT 규칙(8189 허용)으로는 제어되지 않는다.** → 10-13 R1("8189 미개방")의 해결책은 INPUT 허용이 아니라 `45-fw-docker-user.sh`다.
- 이벤트 스케줄러: 구 서버 EVENT 2개와 **이중 실행 금지** → 신 서버는 OFF로 복원, 컷오버 순간에만 ON(`55`).

**배포 방법** (`/root`는 다른 계정이 읽을 수 없음 — hetero 전환 때의 교훈). v5.2 킷은 `/opt/h100` 기준 레이아웃으로 묶여 있어 그대로 풀면 된다:
```
scp h100-migration-kit_v5.2.tar.gz <계정>@192.168.0.115:~/          # /tmp 는 재부팅 시 지워짐 — 홈에 둔다
ssh <계정>@192.168.0.115
sudo install -d -m 755 /opt/h100
sudo tar xzf ~/h100-migration-kit_v5.2.tar.gz -C /opt/h100          # → /opt/h100/migration/*.sh, /opt/h100/docker/*, /opt/h100/conf/*, /opt/h100/*.md
cd /opt/h100/migration && sudo chmod 755 *.sh
sudo cp /opt/h100/conf/migration.conf.example /opt/h100/migration/migration.conf   # 값 확인 (개발서버 기준 값이 이미 들어 있음)
ls /opt/h100/migration          # 스크립트가 여기 바로 있어야 한다 (scripts/ 하위 폴더 없음)
```
> 스크립트는 `/opt/h100/migration/` 에서 `sudo ./00-preflight.sh` 처럼 실행한다. (VM 리허설 중 `./scripts/h100-verify.sh` 로 안내했다가 `command not found` 가 난 적이 있어 정정 — 폴더 구조는 위 `ls` 로 확인.)

## 3. 단계 1 — 사전 구성(리허설, 구 서버 무중단)

> 리허설은 컷오버 전날(D-1)까지 반복 가능. 어느 단계에서든 구 서버 서비스는 건드리지 않는다.

1. **준비**: `sudo ./h100-deploy.sh --prepare` → `/etc/h100/` 설정 채우기(`conf/env-templates.md`). **CA 개인키는 두지 않음**(관리자 PC 전용).
2. **인증서**: 방식 A면 SAN에 `192.168.0.15`+`.115` 모두 포함해 관리자 PC에서 발급(h100-ca 서명) → `/etc/h100/tls/`. 방식 B면 현재 인증서(SAN .115, 2027-09-14까지) 사용. `migration.conf`의 `SERVER_CERT_IP`를 맞춘다.
3. **사전점검**: `sudo ./00-preflight.sh` → FAIL 0까지 정리 (포트 8189/8300 점유 확인 포함).
4. **이미지**: 관리자 PC에서 `mvn package`로 만든 WAR(`gov-disabled-web-adv-1.0.0.war`)와 저장소 체크아웃을 신 서버에 복사 → `sudo ./10-build-images.sh --src <저장소> --war <WAR 파일>` (G0 미통과 시 자동 중단).
   - **module-c 만 먼저**(G0 불필요): `sudo ./10-build-images.sh --src <module_c 소스 상위폴더> --skip-web --tag <이름>` → `.env`(`H100_TAG`) 지정 → `sudo ./h100-deploy.sh --module-c`. `--src` 아래에 `h100_module_c/`(소스 **폴더**)가 있어야 한다. VM에서는 이 경로로 빌드·기동·HMAC·재시작 복구까지 검증함.
   - G0가 아직이어도 DB·미디어 리허설(5~8)은 먼저 진행 가능: `compose.yml`을 `/opt/h100/docker/`에 수동 복사하고 `.env`에 `H100_TAG=pending`·`H100_UID=3100`·`H100_GID=3100`·`H100_EVENT_SCHEDULER=OFF`를 적은 뒤 5단계(`--db-only`)부터 진행. module-c/web 기동(9~)은 이미지 빌드 후.
5. **DB 기동**: `sudo ./h100-deploy.sh --db-only`
6. **구 서버 덤프(읽기 전용)**: 구 서버에서 `./old-server-dump.sh` → 신 서버 `~/h100-incoming/`로 `scp`(덤프·`counts_*`·`SHA256SUMS_<시각>`). 신 서버에서 `sha256sum -c SHA256SUMS_<시각>`.
7. **DB 복원(리허설)**: `sudo ./20-db-restore.sh --dump ... --counts ... --mode rehearsal --replace`
8. **미디어 사전 동기화**: `sudo ./30-media-sync.sh --pre` (약 9.6GiB / 6,919개, 구 서버 읽기만. 소요는 LAN 속도에 따라 다르며 실측 후 컷오버 시간 계획에 반영). 여러 번 돌려도 증분.
9. **기동**: `sudo ./h100-deploy.sh --all --stop-host-module-c` (9월 시험 설치 8189 충돌 해소. 파일 보존, `systemctl enable --now h100_module_c`로 복원 가능)
10. **방화벽**: `sudo ./45-fw-docker-user.sh --check` → 허용 목록 `/etc/h100/device-allow.list` 작성 후 `--apply`
11. **검증**: `sudo ./h100-verify.sh` (+ `sudo ./60-hmac-test.sh`, 실제 키 확인은 `--positive`) → 리허설 기준 FAIL 0. 웹은 브라우저로 로그인·이벤트 목록·영상 재생(`/videoFile`)·이미지(`/imgFile`) 직접 확인.
12. **디바이스 호환(R8)**: Ubuntu 20.04→26.04(OpenSSL 대폭 상향) — 현장 디바이스 **1대**로 8189 TLS 핸드셰이크·전송 시험(테스트 디바이스를 신 서버로 향하게 하는 방법은 G5 결정에 따름).

## 4. 단계 2 — 컷오버 (D-day)

사전 조건: §1 게이트 통과, §3 리허설 PASS, 작업 시간대 공지, 구 서버 최근 백업 확보, 롤백 담당·판단 기준 합의.

| 순서 | 작업 | 실행 | 비고 |
|---|---|---|---|
| 1 | 신 서버 최종 점검 `00-preflight.sh`, `h100-verify.sh` | 신 | 둘 다 FAIL 0 |
| 2 | **구 서버 H100 정지**: `systemctl stop h100_module_c` → `systemctl stop tomcat9_jdk17` | 구(**수동·승인**) | 이 순간부터 디바이스 전송은 ADR-008 PULL-fallback으로 일부 흡수. 정지 시각 기록 |
| 3 | 구 서버 **최종 덤프** `old-server-dump.sh` → 신 서버로 전송 | 구→신 | 정지 후 덤프라 행 수 완전 일치해야 함 |
| 4 | `20-db-restore.sh --mode final --replace` | 신 | **행 수 불일치 0** 필수(FAIL이면 중단) |

| 8 | **디바이스 전환** (§5, 방식 A 또는 B) | 구/신/디바이스 | 미정 |
| 9 | 디바이스 수신 확인: DB `tbl_event_data` 신규 행, `docker logs h100-module-c`, 웹에서 신규 이벤트·미디어 | 신 | 최소 1개 디바이스 이벤트 수신까지 확인 |
| 10 | 관찰(30~60분): 컨테이너 재시작 횟수, 로그 error, 디스크, 디바이스 전송 실패율 | 신 | 이상 시 §6 |

## 5. 디바이스 전환 — A/B (G5 미정)

| | A. IP 인수 (192.168.0.15 승계) | B. 디바이스 설정을 192.168.0.115로 변경 |
|---|---|---|
| 디바이스 변경 | 없음 | **모든 디바이스 `.env`의 `CLOUD_RECEIVE_IP` 수정**(module_d) |
| 인증서 | SAN에 **.15 포함 새 인증서** 필요(B4), `SERVER_CERT_IP=192.168.0.15` | 현재 인증서(SAN .115) 그대로 |
| 구 서버 | .15를 비워야 함(IP 변경 또는 NIC 정지) → 구 서버의 다른 사업(lynceus, airflow, epsene…)·`/dstwin/` 의존(R6)에 영향 | 영향 없음 |
| 롤백 | IP 원복 | 디바이스 설정 원복(다수면 번거로움) |
| 기타 | 구 서버에 타 사업이 같이 있어 **IP 승계는 영향 범위가 큼** | 디바이스 수가 적으면(현장 1대 추정) 현실적 |

참고: `tbl_device.dv_ip`는 서버→디바이스 호출용이며 서버 IP 이전과 무관(B-07). 별도 8089 수신 경로가 있으면(G2) 그 경로의 전환도 같이 계획한다.

## 6. 롤백

**판단 기준(예)**: 컷오버 후 디바이스 이벤트 미수신 15분 초과 / 행 수·파일 수 불일치 해결 불가 / TLS 핸드셰이크 실패 / `h100-verify.sh` FAIL 해소 불가.

1. 신 서버: `sudo ./h100-rollback.sh --yes` (컨테이너 정지, 데이터·이미지 보존). 필요 시 `--remove-fw`, `--restore-host-service`.
2. 디바이스 전환을 했다면 원복(A: IP 원복 / B: 디바이스 설정 원복).
3. **구 서버(수동)**: `systemctl start tomcat9_jdk17`, `systemctl start h100_module_c` → DB·미디어는 구 서버가 정지 전 상태 그대로(구 서버는 쓰지 않았으므로 데이터 손실 없음. 단 정지~롤백 사이 전송분은 디바이스 PULL-fallback/재전송 확인).
4. 구 서버는 **최소 1주 보존**. 신 서버에서 생긴 신규 이벤트가 있다면 롤백 전 덤프로 보존(필요 시 구 DB로 역반영 별도 판단).

## 10. VM 리허설에서 확인된 사항 (2026-10-26)

환경: VirtualBox VM(Ubuntu 26.04, Docker). 구 서버에서 받은 실제 dump 로 module-c 경로만 검증. 상세 기록은 Obsidian `H100_VM_리허설_결과_2026-10-26`.

- **통과**: module-c 이미지 빌드(golang:1.24→alpine, 약 36MB) · 기동 · DB 접속 · HMAC(헤더 없음 401 / 0 HMAC 401 / 정상 서명 200) · 미디어 쓰기(UID 3100) · DB 재시작 후 자동 재연결 · 호스트 재부팅 후 자동 복구 · TLS 검증(`h100-verify`) · DOCKER-USER 방화벽(허용 405·400 / 차단 000 + DROP 카운터 / 재허용 / 재부팅 후 규칙 유지).
- **재부팅 직후 module-c 재시작**: module-c 가 DB 보다 먼저 떠서 `failed to connect database` 후 `restart: unless-stopped` 로 자동 재시작(RestartCount 3 관찰) → DB healthy 되면 정상. `h100-verify` 의 재시작 횟수 WARN 기준(>2)에 걸릴 수 있으나 자가 복구된 경우 문제 아님.
- **healthcheck 로그 노이즈**: `nc -z` 가 TLS 핸드셰이크를 중간에 끊어 module-c 로그에 15초마다 `TLS handshake error ... EOF`. 무해(필요 시 healthcheck 방식 교체).
- **로그 위생**: 기동 시 DSN(비밀번호 포함)이 로그에 출력됨 → G1/T2 소스 수정 대상, 그 전까지 로그 파일 접근 제한 및 로그를 캡처해 공유할 때 마스킹.
- **방화벽 점검 시 주의**: VirtualBox NAT 포트포워딩은 게스트가 DROP 해도 호스트 쪽 TCP 는 열려 보임(`Test-NetConnection` 부정확). HTTP 코드(`curl.exe`: 405/400=도달, 000=차단)와 `iptables -L H100-8189 -v -n` 의 DROP 카운터로 판정. 개발서버에서는 실제 디바이스/LAN PC 에서 접속해 확인.
- **`migration.conf` 필요**: 없으면 `SERVER_CERT_IP` 기본값(192.168.0.115)으로 TLS 검증 → 접속 IP 가 다르면 FAIL. VM 에서는 127.0.0.1 로 둠. 개발서버는 예시 파일 값 그대로.
- **개발서버 특이점**: 9월 시험 설치 systemd `h100_module_c` 가 8189 점유 → `h100-deploy.sh --module-c --stop-host-module-c`(v4 에서 `--module-c` 도 점검). 개발서버는 물리 서버라 VM 에서 겪은 CPU 정지(Windows 하이퍼바이저+VirtualBox 충돌)와 무관.
- **미검증**: 30-media-sync, 20-db-restore 의 개발서버 실행, web 이미지(G0 필요), 디바이스 실제 접속.
